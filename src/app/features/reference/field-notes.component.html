Your local workflow

go version
Check the selected compiler; this course targets 1.27.4.
go mod init example.com/hello
Create a module in a new project directory.
go run .
Compile and run the current command.
go build ./...
Compile all packages in the module.
gofmt -w .
Format Go source consistently.
go test ./...
Run unit tests, examples, and fuzz seeds.
go test -race ./...
Check exercised paths for data races.
go vet ./...
Inspect suspicious constructs.
go doc io.Reader
Read an API contract from the terminal.
go mod tidy
Reconcile module requirements with imports.

Semantics to remember

  • Arguments are passed by value. Pointers, slices, and maps can still share underlying data.
  • Keep the slice returned by append. Clone when independent storage is required.
  • A nil interface differs from an interface holding a typed nil pointer.
  • Check errors. Use %w to wrap a cause and errors.Is / errors.As to inspect it.
  • Give every goroutine a way to finish. Cancellation is cooperative.
  • The sending lifecycle owns channel closure. Join senders before closing results.
  • Strings contain bytes; runes represent code points, not necessarily visible characters.

Take the next step locally

The playground accepts one standard-library source file. Test mode saves it as main_test.go. Use a local module for multiple files, dependencies, interactive input, and network services. 

go test -fuzz=FuzzHex -fuzztime=10s
go test -run=^$ -bench=. -benchmem
go test -cpuprofile=cpu.out
go tool pprof cpu.out

Fuzz seeds run in the playground; generation and benchmarks are local commands. Drafts, notes, and progress stay in this browser. Download code to keep an independent copy.
